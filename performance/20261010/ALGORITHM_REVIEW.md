# 算法评估与筛选

用户要求每项优化实施前先估算全量收益与成本，优先算法改进，搁置低收益、高成本的缓存及分配优化。本记录区分文献结论、项目作者自报、jadx 实测和待验证假设。

## jadx 重复整类处理：值得优先验证

第七项候选端点 `b321cdaf6bfc6434c15a608a8f36193470928694` 上的一次独立诊断，固定原基准输入/JDK/heap/8 线程/输出选项，不改变流程：

- 93,679 个顶层类进入处理，其中 51,606 个处理两次；第二次入口均为 `GENERATED_AND_UNLOADED`，请求 `codegen=false`。
- SSA 实际启动 1,442,493 次，按 MethodInfo 统计 815,536 个不同方法：188,583 个一次、626,951 个两次、2 个四次。方法恢复至指定 visitor 的调用共 5 次。
- 首次 visitor CPU 合计 128.254 秒，重复 visitor CPU 合计 91.441 秒，后者占 visitor CPU 的 41.62%、该诊断进程 CPU 415.46 秒的约 22.01%。使用 ThreadMXBean，扣除同线程嵌套处理已计时部分；未包含类加载、源码生成、GC/JIT 线程，也不是严格可消除的成本上限。
- 带诊断 wall 67.55 秒、RSS 17,643,144 KiB、退出 3、71,047 Java 文件，仅作机会测量，不能进入正式 A/B 中位数或替代内容比较。

这证明重复处理真实存在，但不证明它全部多余。普通依赖可能提供 EnumClassAttr、EnumMapAttr 等非 pinned 信息；匿名类与内联也可能需要方法体，因此不实施“已生成过就直接跳过分析”的粗略改法。

候选是调整生成顺序，使使用者尽量在依赖类生成并卸载前完成：保留现有按需处理和所有 passes，让依赖 AST 在原有 PROCESS_COMPLETE 状态下供多个使用者复用。

依赖图普查：93,680 个顶层节点、789,317 条去重边、38,246 个强连通分量；最大环包含 44,870 个类。串行静态模型中，原顺序额外处理 20,594,550 个原始指令单位；反转现有顺序约 11,727,212，先拓扑排列分量、分量内保留原顺序约 16,252,993。模型不包含并发、内联或动态依赖，不能当作性能结果。大环也使引入复杂拓扑调度的成本不合适。

最小实验提交 `56039433d4561133884612d25dd4f8853125dec3`（`codex/reverse-decompile-order`）反转原批次及依赖批次内顺序，无依赖批次保持靠后。新增共享依赖回归在原逻辑中观察到同一类处理两次，在候选中四个类各处理一次并全部生成。core/CLI 共 1,065 项测试零失败、1 项版本条件跳过，格式与 Checkstyle 通过；冻结包只有 core JAR 改变。

**实验撤回，未进入正式三轮 A/B。** 独立 JFR 运行 62.02 wall 秒、369.15 CPU 秒、17,636,476 KiB RSS，与此前父端点 JFR 的 66.48 wall 秒、405.41 CPU 秒仅作初步比较。两者均退出 3、71,047 个 Java 文件、无缺失或新增文件。但候选有 2,739 类 Java token 差异：595 类仅 throws、147 类 throws 与 import、34 类仅外层直接重抛，剩余 1,963 类需复杂审查，涉及构造函数、访问范围、方法命名及方法体等。省略体 910→906，但有 6 个候选新增省略、10 个恢复，不能按总数下降豁免。错误数 981 也不能证明质量改善。为约 6.7% 的单次初步 wall 改善承担如此大的输出验证成本，不符合当前成本收益要求。该实验当时恢复到父端点 `b321cdaf6bfc6434c15a608a8f36193470928694`，本轮最终又因 Telegram 质量问题撤回第七项，保留源码为六项端点 `2655258`；保留实验分支、冻结包、全套测试结果及诊断数据，不计入优化收益。

证据与复现入口：`continuation/repeat-diagnostic.py`、`RepeatDiagnostic.java`、`repeat-diagnostic.patch`、`repeat-diagnostic/metadata.json`、`repeat-diagnostic-summary.json` 及 `logs/jadx-perf/20261010/repeat-diagnostic.txt`。这些诊断文件在工作目录的 `out/jadx-perf/20261010` 下，未混入生产补丁。

## 收益解释

若某阶段占墙钟比例 p、局部加速 s 倍，则全量耗时下降为 `p × (1 − 1/s)`。例如阶段占 10%，即使加速十倍，全量也只下降 9%。JFR CPU 占比不是这里的墙钟 p，需要结合并行度和关键路径。

当前没有新的累计 ≥50% 结果。类型候选窄约束剪枝、小映射表延迟分配、原始类名字段等方向均不能以局部操作数或分配下降冒充全量收益；原始类名实验已有三轮 wall 回退并撤回。质量疑点与未检查项沿用 CONTINUATION.md，不因算法研究而豁免。

## 继续筛选：先核算机会，再决定实现

| 方向 | 算法变化 | 当前证据、成本与决定 |
| --- | --- | --- |
| 类型候选求交 | 原来扫描实现类列表，对每个候选逐个检查边界；设实现数 M、赋值类型祖先数 A，可以在有序实现列表中二分查找 A 个名称，按原次序验证交集。 | 新诊断允许后续边界含泛型等复杂类型，但要求赋值约束前的边界不产生未知层级警告。6,341 个变量符合必要约束，其中 5,068 个满足安全前缀；7,708,847 次检查可剪掉，约占此前约 4,679 万次已知候选检查的 16.5%，误剪 0。填充阶段包含约 9.2% CPU 样本，乘以覆盖比例只能作为约 1.5% CPU 的粗略机会估算，既不是 wall 预测，也不是严格上界。为此处理泛型、未知类、日志及候选停止次序，成本偏高，未实施。 |

| 组合搜索的冲突跳转 | 从逐个枚举组合，改为跳过不影响当前失败约束的低位变量组合。 | search 包含约 4.87% CPU 样本。必须保持第一个解、原始 1,000,000 次逻辑枚举保护、警告及异常行为；较早通过的约束可能在跳过的组合上产生不同警告或异常。没有简单证明可覆盖所有类型，未实施，也没有声称已取得剪枝收益。 |

| 前端扫描与应用使用关系 | 改进串行预处理算法或并行收集、顺序归并。 | 新 JFR 主线程共 1,597 个执行样本，其中 UsageInfoVisitor.init 包含 1,014、构建 497、apply 517、sortedList 403；包含项不能相加。前约 20 秒主要由主线程执行，具有 wall 关键路径机会。Root 的容器、异常归属、别名及全局信息写入尚不支持直接并行；DEX 索引单独解码还涉及输入插件 API。没有跳过全局扫描或引入新的线程框架。 |

宽松候选诊断保留原候选检查与原输出流程，只计数并断言原逻辑允许的候选没有被理论过滤器排除。带诊断 wall 70.42 秒、CPU 439.70 秒、RSS 17,692,072 KiB、退出 3、71,047 Java 文件；不计入正式性能结果。原始计数为 `[6341, 8068887, 8016368, 8017799, 8012662, 0, 5068, 7749742, 7708847]`，字段定义及修改补丁保存在 `out/jadx-perf/20261010/continuation/probe-pruning-broad.py`、`pruning-broad-probe.patch` 和对应运行目录。JFR 分线程及动态边界交集统计见 `profile-phase-summary.json`，同一采样同一方法只计一次。

DDC 的稳定变量身份及 worklist 针对其实现中虚假的状态变化、重复整图重建；jadx 已有 SSA 身份与部分更新传播。此前 jadx 存活性逆序遍历已经将块扫描降低约 71%，但三轮 wall 中位数只下降约 0.04%，已撤回。这是不能从算法局部倍数推导全量收益的直接例子。

DDC 的速度也包含前端并行、数据布局、分配器、I/O 流水线及工具特有的复杂方法超时策略。它的性能记录不是相同算法、相同输出质量、相同线程的语言实验。当前不采用缩短超时、限制方法体恢复或减少分析的做法；单块快路径也必须先证明省略的 pass 对该输入没有作用。不能从 DDC 的自报倍数向用户保证 jadx 的收益。

## 2025–2026 文献补查与安装取舍

[SURE 2025 的类型推断比较](https://sure-workshop.org/accepted-papers/2025/sure25-8.pdf)研究 x86-64 C 二进制，比较现成反编译器及 Retypd，提供源码真值和覆盖率等指标；它不是 DEX 类型推断的加速补丁，也不能用类型指标替代方法体语义检查。本轮阅读其背景与方法部分，没有安装全套原生二进制评测工具。

[2025 年 SPL 分解论文摘要](https://arxiv.org/abs/2507.16660)讨论寄存器分配、LOSPRE 和存储体选择的图分解。这里只检查了摘要，未读全文、构建实现或在 jadx CFG 上测量；没有据此声称可直接加速当前可达性查询。新的图表示与求解框架不属于低成本移植。[2026 年 CFF 抽象解释工作](https://ieeexplore.ieee.org/document/11369430)面向控制流平坦化恢复；只核查公开摘要，不能把其反混淆质量当作当前普通 APK 的速度收益。SoK 结构化综述的 Fraunhofer 页面被访问保护拒绝，没有声称已阅读全文。

选择先读论文和固定提交的源码，无需为了理解算法安装 Rust、Python 分析栈或模型。若有适合当前热点、能保持输出合同的具体算法，再承担实现和运行成本；未运行的外部工具不写入性能比较。用户进一步授权有大收益的较大改造，但收益不能在验证前保证。优先诊断可持久跨类分析结果与串行前端的实际合同，再以隔离原型检验可重复收益及质量；较大的类型求解器与使用列表表示仍需同样的证据门槛。

## 新的隔离诊断与原型

跨类读取诊断 v2 保留全部 passes，记录已发生重复处理的顶层类后续被其他类读取的属性、标志及部分方法体 getter。51,328 个顶层类重复处理；跨类请求包含 `getRegion` 84 次、`getArgRegs` 58 次、`getBasicBlocks` 46 次，以及 3 次非 pinned ENUM_CLASS、约 1,414 万次非 pinned CLASS_TYPE_VARS 读取。仍有 DONT_GENERATE 与 SKIP_FIRST_ARG 等有效标志读取。因此不能只保留 pinned 属性就取消重复处理。该探针并未覆盖所有直接字段、属性辅助方法或写操作，不能单独证明生命周期改造安全。v2 退出 3、71,047 Java 文件，67.34 wall 秒、410.46 CPU 秒、17,647,704 KiB RSS，仅为诊断。v1 探针错误地假设顶层类有 declaring class，触发异常并输出不完整，已排除；生产源码在两次构建后均恢复。

统一排序邻接图的原型：原来每个邻接集合独立排序，比较量约为 `Σ d log d`；候选先构造转置图，将不同目标节点排序一次，再按该顺序分发，比较量约为 `U log U`，另需 O(E) 额外遍历和存储。通过正常 API 加载固定千问、在同一份使用数据上核查所有元素身份及次序，七组关系均零差异；局部单次计时如下，属于筛选诊断，不是全量正式性能结果。

| 邻接关系 | 边数 E | 不同目标 U | 原来局部秒 | 转置局部秒 |
| --- | ---: | ---: | ---: | ---: |
| clsDeps | 802786 | 87632 | 0.117 | 0.241 |
| clsUsage | 1129128 | 127624 | 0.380 | 0.365 |
| clsUseInMth | 2432426 | 683121 | 1.632 | 1.846 |
| fieldUsage | 1554950 | 591784 | 0.600 | 1.622 |
| mthUsage | 1969714 | 608773 | 1.154 | 1.724 |

大多数关系的额外分配和查找成本超过减少比较的收益，未做生产改动、三轮扩测或保留补丁。源码为工作目录 `out/jadx-perf/20261010/continuation/UsageSortProbe.java`，日志为 `logs/jadx-perf/20261010/usage-sort-probe.txt`。

使用位置索引进入隔离原型：现有 DuckDuckGo profile 的 24,200 个执行样本中，`InlineMethods.replaceClsUsage` 包含 10,251 个（42.36%），`safeReplace` 包含 13,493 个（55.76%）；两者相互包含，不能相加或当作 wall 比例。当前千问同类操作占比很小。R 次内联对长度 L 的列表重复线性查找，扫描可达 O(R×L)；保留 ArrayList 顺序和全部重复项、为元素建立有序位置集合后，首项定位和替换可变成首次 O(L) 建索引加每次 O(log D) 更新，D 为同一元素的重复次数。中间插入、删除使位置失效，重新查询时重建。索引属于列表，类重新应用使用关系时重建列表，没有跨 Root 的全局缓存。

原型包裹 UsageInfo 新创建的非空类使用列表，以及内联时从空列表新建的列表。小列表保持线性查询，增长到 256 项后首次查询时建立位置索引；方法、字段的复制发布行为和所有分析 passes 保持原流程。旧的非空列表不会在内联中被复制包裹，以保留已有引用的可见性。GUI 缓存提供的普通非空列表仍按原流程更新，未声称 GUI 加速。

初版实验提交 `ef84577` 只包裹初始较大列表，单次 DuckDuckGo JFR 运行 206.35 wall 秒、448.49 CPU 秒、17,496,316 KiB RSS，未提速。长尾线程栈仍位于普通 ArrayList 的 `replaceClsUsage`，证明热点列表在内联中从小列表增长；这版不计入收益。补全增长路径的实验提交 `e06fc60` 通过 core/CLI 共 1,068 项测试（零失败、1 跳过）、格式及 Checkstyle；回归覆盖 null、相等对象、重复首位置、追加、迭代器、subList、排序、清空与索引失效。

补全版单次 DuckDuckGo JFR 运行 90.71 wall 秒、320.31 CPU 秒、17,630,668 KiB RSS；此前六项优化的同样采样运行为 188.62 wall 秒、429.32 CPU 秒、17,568,856 KiB RSS。这是不同端点的初步筛选，不能替代直接父提交的三轮交错 A/B。两次均退出 3、31,108 Java 文件，没有缺失、新增文件或省略体变化，错误清单不变；52 个类有 Java token 变化，继续核查。

带影子校验的两次全量运行逐次在同一锁内将索引结果与原 `ArrayList.indexOf` 比较。千问 52,255 次索引查询、累计列表长度 76,230,924；DuckDuckGo 755,467 次索引查询、累计列表长度 67,697,194,977；两者零差异，保留原结果和完整输出流程。累计长度是潜在线性扫描量，不是实际逐元素比较次数。DuckDuckGo 的 52 个候选类 token 变体全部与已有普通全量参考输出完全一致，未省略任何 body token。直接父提交的三轮交错 A/B 尚待完成，未将诊断耗时写作优化收益。原始补丁、冻结分发包、线程栈、回归 XML、内容审查和诊断脚本保存在 `out/jadx-perf/20261010/continuation` 及对应日志目录。

增长版千问三轮直接父提交对照已完成：wall 64.96 (64.15–65.87) → 65.55 (65.36–65.87) 秒，中位数回退 0.91%；CPU 398.96 (392.10–414.36) → 407.07 (404.38–407.96) 秒；RSS 17650612 (17639000–17679600) → 17695900 (17687252–17717428) KiB，中位数增加 0.26%，三对均更高。即使 DuckDuckGo 初步提速很大，这版也暂不保留。停止了随后开始的 DuckDuckGo A1，退出 143、少一个 Java 文件；它是主动终止的无效运行，完整保留记录并排除性能和质量结论。该组正式三轮结果只覆盖千问，不得写成两个样本均完成三轮。

同一算法的紧凑表示实验 `0590b9d`：只出现一次的元素直接保存整数位置，出现重复时才分配 TreeSet，降为一次时释放它；第一位置查询为 HashMap 的预期 O(1)，替换仍保留所有位置。避免为每个唯一节点分配 TreeSet、TreeMap 及树节点，代价是为重复键维护第二个 Map。它不能预先保证所有输入的 RSS 下降。新增相同哈希、不同字符串及单次/重复转换回归；core/CLI 共 1,069 项测试零失败、1 跳过，格式与 Checkstyle 通过。冻结包 core SHA-256 为 `77b512186d266cc11672496a99a3e59e264bd7b14a1693708033933a2afe7498`。

紧凑版在两个样本均完成三轮串行交错 A/B，A 为直接父端点 `b321cda`，B 为 `0590b9d`；同一 checkout、固定 JDK/heap/8 线程/输入/输出选项。中位数及范围如下，CPU 为 user + system，RSS 为 KiB。
