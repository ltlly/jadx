# jadx Java 反编译性能优化

后续算法研究、三轮候选测量及质量复核见 [后续记录](CONTINUATION.md) 和 [算法评估](ALGORITHM_REVIEW.md)。第七项候选曾测得千问累计 25.62%，因 Telegram 新增受检异常覆盖声明冲突撤回；使用列表索引也未合入。最终保留下面六项优化及其十 APK 结果，不将候选收益计入交付。

千问全量 Java 反编译耗时中位数下降 **22.25%**，CPU 消耗下降 **18.39%**，峰值 RSS 中位数下降 **0.29%**。尚未达到争取的 50%。六项性能改动之外，输出内容审计发现并独立修复了原版的共享三元条件问题；正式比较使用相同正确性修复之上的基线与优化版。修复前数据仅保留为[候选记录](LEGACY.md)。十个固定 APK 的三轮串行交错 A/B 已完成。

## 共同正确性基线

原始源码为 `45746868c3d3072288400150c34f5cbdac9bba79`。新基线 `8e35efc4e156c20d2af40c0a160eb78cdcfe9f40` 只增加三元表达式独立复制和对应 SSA 清理修复，性能优化从此提交开始。六项优化终点为 `26552586d64e43b0a4806f6cc70c5a2202731dd1`，分支 `codex/jadx-performance`；没有创建 PR。

七个源码补丁及合并 mbox 的校验值见 [patches.tsv](patches.tsv)。已在独立 Git index 中依次应用到原始源码，得到的 tree 与优化终点完全相同；验证记录为原始结果目录下的 `verified/patch-application.json`。

`TernaryInsn.copy()` 原来共享可变 `IfCondition`。内联替换某一调用的参数会污染模板，后续调用可能使用前一调用的默认参数掩码。实际千问调用应使用 60，原版改变类生成顺序后会错误地使用 112，进而丢掉回调参数。该差异有语义影响，不能用相同文件数、相同错误总数或语法通过率豁免。

修复独立复制比较指令和嵌套条件，并用已有寄存器遍历清理副本的 SSA 使用。新增两个回归用例在旧实现上均失败；修复后，真实 APK 的两种生成顺序均保留正确掩码 60。共同基线 core/CLI 共 1,054 项、最终版共 1,063 项，均为零失败；两版各跳过一项 Java 17 profile，其他通过。

## 独立改动

每项性能改动单独提交，使用直接父提交作 A。没有新增依赖、全局缓存或分析阶段开关，也没有缩短超时或改变类型候选上限。

|---|---|---|
| `b6f7f17` | outer switch 检查改为前驱早停 | 原始前驱边、包含起点和终点、到起点停止 |
| `6585c3a` | CFG 递归查询改用索引循环 | 邻居次序、支配关系捷径、predicate 行为 |
| `026c993` | bottom block 先验证后方源块 | 候选次序与第一轮支配检查不变，同一候选的验证次序改变 |
| `a021492` | 命名引用已有根包名集合 | 当前写入者替换集合；继承不同快照仍合并旧名称 |
| `5ef1f56` | 按需转换类型候选 | 顺序、去重、边界检查和原停止条件，包括后续批次可多接受一个候选的旧行为 |
| `2655258` | 逐个检查变量使用位置，取消临时 HashSet | 使用原包含判断，保留异常处理 region 的特殊路径 |

回归覆盖 512 个三节点前驱图、环及 clean/full CFG 边、候选优先级、命名碰撞与集合快照继承、类型候选消费次序、使用位置次序及异常处理多父 region。生产实现没有引入 region 索引。最终测试统计见 [tests.tsv](tests.tsv)，各阶段 core JAR 哈希见 [builds.tsv](builds.tsv)。

根包名复用的是当前 Root 已有快照，仓库写入者 `RenameVisitor` 通过替换 Set 发布；不同快照之间的继承仍合并旧名称。类型流在同一调用内立即消费，来源为分析前构建完成的 Clsp 祖先集合和实现类列表，已检查现有调用者不原地修改它们。这里没有把 CFG 边或指令的可变性假设成永久不变，也没有跨方法保存可达性结果。

## Profile 驱动的取舍

共同基线及每项修改后均单独运行千问全量 JFR，摘要见 [profiles.tsv](profiles.tsv)。基线有 25,103 个执行样本，其中 1,425 个截断；最终有 17,879 个，其中 307 个截断。inclusive 占比统计同一样本中重复递归的方法一次，不能将多个占比相加。

CFG 索引循环前后，`traverseSuccessorsUntil` 的分配抽样权重从 35.11 GB 降到 4.63 GB。随后 bottom 顺序调整把 `getBottomBlock` 的 inclusive 占比从 12.29% 降到 1.78%；根包名复用把 `addNamesUsedInClass` 的分配权重从 27.91 GB 降到 0.18 GB。按需类型转换后，`fillTypeCandidates` 从 13.95% 降到 8.52%；使用位置检查从 5.40% 降到 0.53%，自身分配权重从 3.90 GB 降到 0.007 GB。这些是局部采样变化，实际全量收益见独立 A/B 表。

最终千问诊断中，新旧 bottom 判断 3,123,538 次、命名判断 2,035,219 次、使用位置判断 4,292,227 次、outer switch 判断 81,882 次、类型候选集合 51,406 次均无结果差异，类型候选还比较了次序。bottom 路径检查 60,802,114 → 9,906,347 次，使用位置包含检查 157,645,674 → 23,367,639 次，类型对象转换 248,595,512 → 46,481,226 次。诊断版同时运行参考算法，有额外工作，不参与性能统计。

继续检查了 region 包含关系和存活性分配。最终 `isRegionContainsBlock` 只占 inclusive 样本 0.27%，`IfRegion.getSubBlocks` 为 0.46%；没有为此引入可变 region 的快照缓存。存活性有 6.68 GB 分配抽样权重，但两个局部实验没有形成可重复全量收益，均撤回，详见下文。

## 测量与质量方法

所有 APK 的全部 Java 类经过正常加载、分析、代码生成和源码写出，资源输出关闭。固定 OpenJDK 27 build 27、`-Xms256m -Xmx16g -XX:ParallelGCThreads=3` 和 8 个反编译线程。Gradle 使用 Temurin 25.0.4.1，编译和测试使用 Temurin 11.0.32.1。每次新 JVM、新输出目录，正式 A/B 串行交错三轮，构建、测试、采样和输出审计分开进行。CPU 为 user + system 秒，RSS 为进程峰值；报告中位数和最小值至最大值。

输入 manifest 版本号、包名、SHA256、来源、DEX 数及 class_defs 见 [corpus.tsv](corpus.tsv)。十样本仅在千问取得经验证的有意义改善后运行。每次记录命令、JDK、全部分发文件哈希、退出码、错误、逐文件清单及完整 unified diff。另比较逐方法占位体，并检查修改版所有运行的新增占位体并集，保留源代码 token、警告和错误变体供逐项复核。词法分组不构成语义证明。

交付前核对全部 96 次正式记录：JDK 版本唯一，JVM/CLI 选项固定，输入与七个阶段 core JAR 哈希一致，正式计时无重叠，分发包之间仅 core JAR 变化，逐文件清单无缺失或新增。源码提交父链、七个补丁的哈希和应用结果也已核对。原始结果目录中的 `verified/delivery-metadata-check.json` 保存这项核验；[runtime.tsv](runtime.tsv) 另保留性能 JDK 安装包及关键文件哈希。

测量方法参考 [DDC performance engineering](https://github.com/ejfkdev/ddc/blob/b8bb5d02192840a2706595ee17391d86b7126b5c/docs/optimization.md)。正式中位数不含 JFR、旧新算法诊断或控制实验。没有清除操作系统文件缓存；每次计时前哈希输入和分发包，文件已被读取。结果代表新 JVM、预热文件缓存的交错运行，并非冷磁盘启动。三轮范围不是置信区间，独立增量百分比不能相加。

复现命令见 [REPRODUCE.md](REPRODUCE.md)。原始记录和分发包保存在 `/home/ltlly/Code/jadx-perf/out/jadx-perf/20261010`，日志保存在 `/home/ltlly/Code/jadx-perf/logs/jadx-perf/20261010`。修复前数据与最终重测分开保存，APK、完整源码输出、JFR 和工具链没有加入 Git。

## 已撤回的实验

局部 scratch BitSet 复用实验 `e8980fe` 独立基于六项优化，未进入交付分支。完整测试零失败，千问新旧存活位图及轮次均一致；processLiveInfo 分配抽样权重从 6.68 GB 降至 0.97 GB。但三轮耗时 68.46 [68.45, 68.49] → 68.02 [67.83, 68.68] 秒，CPU 411.15 [409.18, 411.95] → 409.44 [403.84, 411.27] 秒，RSS 中位数增加 0.19%，范围重叠。一对耗时反向，没有证明稳定的全量收益，因此撤回。分配抽样权重不是峰值 RSS，不能把两者混为一谈。原始实验和本地分支 `codex/reuse-live-bitsets` 保留。

逆序存活性扫描实验 `8a831fe` 同样未保留。诊断中最终位图零差异，块扫描次数 124,710,830 → 36,051,076，超过十轮的方法分析 56,000 → 11；迭代保护上限未改变。但三轮耗时 68.26 [67.89, 68.54] → 68.23 [68.08, 68.53] 秒，CPU 409.16 [404.24, 409.61] → 411.49 [406.65, 413.07] 秒。耗时中位数仅下降 0.04%，CPU 增加 0.57%，因此撤回。本地分支 `codex/reverse-live-traversal` 和全部诊断记录保留。新旧位图相同只证明该项数据流结果相同，不自动豁免源码输出的全部异常变体。

更早还测试过 MethodInfo.equals 的已有 hash 快速拒绝。DuckDuckGo 三轮范围重叠，首对反向，CPU 仅约 1.5% 中位数变化，未显示稳定收益，已撤回。该实验使用修复前候选版，其数据只在历史记录中保存，不参与最终收益计算。没有增加使用列表的缺席缓存、全局可达性缓存或 GC 调优。

千问 A/B 都以退出码 3 结束，错误总数均在 1,032–1,033；基线占位方法体 910–917，优化版 906–911。B 的占位体并集有两项未出现在最终三轮 A 并集中：PingCmdImpl 的同一占位方法已在共同基线的其他完整运行中出现；Flow 的同一方法、匿名依赖、SGET 指令和状态检查则在原始 JAR 与共同基线的受控并发重载中复现。Flow 没有在最终三轮常规 A 自然出现；对照显式使用 core 生命周期入口。两种证据强度不同，完整差异保留，不能声称所有新增占位体都在普通基线 CLI 中复现。

逐 token 复核对上 104 个既有基线整类变体，另外 9 个只差无副作用的外层直接重抛；其他变体人工检查。56 处声明逐一找到原版或共同基线输出，包括 `throws Throwable`、`IOException`、`CloneNotSupportedException` 和 `UnsupportedEncodingException`。声明影响源码 API，不能当作注释差异。默认参数掩码、回调及 null 构造参数另行核对；内联合成辅助方法的消失来自既有正常内联流程，未跳过方法分析。

地图 `m.b.a` 的吞异常 catch、`AggregateFuture.i` 的 finally，以及 `h.c` 的内层异常处理都有实际语义差异。对应 B 方法或整类已在原版/共同基线出现；`h.c` 还由原版不同 enum identity hash 的合法执行复现。它们列为原版的顺序依赖问题，不列为等价格式变化。原版已有构造器类型推断、跨类可见性和依赖卸载错误；共享三元条件污染则已独立修复，未因它属于原版问题而豁免。

Telegram 的三轮没有新增占位体，方法体复核剩下的是 import 和 throws 声明变化；不能因此忽略源码 API 变化。`AndroidUtilities.doSafe` 的三种新增异常已在原始版、共同基线和最终版的受控处理窗口复现：递归 throws 分析看到尚未附加 catch 属性的基本块，并提前固定分析结果。该对照证明具体来源，尚未逐项证明其他所有变化声明。

Wikipedia 新出现的 `SampleDataQueue.discardDownstreamTo` 占位体及同一 handler 0x0042 的 finally 错误，已由共同基线的正常类生成 API 加 enum identity hash 对照复现；不属于普通全量 CLI 重复运行。Firefox 的 `CleanerRef.clean` 占位体则在历史原版完整 CLI 自然出现，整类 token 完全相同。Termux 的 `Continuation.get$context` 与接口 `getContext` 不一致是实际无效引用，B 整类与历史原版完整 CLI 相同，不能称为无害改名。

Signal 新出现的 `UnknownStorageIdTable.getAllUnknownIds` 占位体在 B2，整类 token 与历史原版完整 CLI A3 完全相同。B1、B3 有完整方法体。`StateFlowImpl` 的错误注释由 `JadxOverflowException` 变成 `StackOverflowError`，对应方法在两版均已是占位体；VLC 也有相同错误家族的变化。这些仍是失败方法，不按反编译成功统计。

Edge B2 总错误数为 354，其他五次为 353；逐文件错误标记没有新增变体，B 占位体并集也没有新增项，但额外一次错误事件尚未归因。错误计数器按事件累加并不证明它是重复事件，当前不能作此结论。

WhatsApp 六次均输出 101,130 个 Java 文件，没有缺失或新增。基线占位体 1,720–1,727，优化版 1,717–1,722；B 并集有四项新增，其中 `C14710kr.A0a` 在三次 B 均出现。四个占位变体均有历史原版完整 CLI 的整类 token 匹配；`A0a` 还由共同正确性基线的正常类生成 API 加 enum identity hash 参数 0 精确复现，同一 handler 为 `0x002c`。当前三轮常规 A 没有自然出现它，不能把受控 API 对照描述为全量 CLI 重复结果。

WhatsApp 的 `AbstractServiceC31041ad.A0B`、`C58546QhD.A0J` 和 `R0Q.CFP` 的清理/finally 变体已由原版普通 API 分别以参数 4、0、5 精确复现；Edge `fmf0.c` 对应参数为 1。注册服务变体少两处清理调用，其他 finally 与重复清理也可能有异常语义差异，因此均列为既有问题。另有 77 个人工复核变体只涉及声明或 import，其他方法体变化含直接重抛、局部变量改名、等价分支合并及恢复占位体。恢复方法体不自动证明输出正确或可重新编译。

额外原版普通 API 对照得到多个 B 的整类 token 匹配：Wikipedia/Firefox 的合成构造器变体、Wikipedia 的 byte 调用、Signal 的 byte 调用，以及 Firefox 的桥接方法命名。Signal 的具体 `0 == true` 构造参数错误也在原版出现；不能称为无害转换。Wikipedia 的 throws 声明有原版具体 header 匹配。Firefox `getHostFromUrl` 的 `throws Throwable` 和 VLC `postValue` 的 public 变体未在补充的两个顺序对照中复现，其他所有变化声明也没有逐项证明；这些限制保留在质量结论中。

## 尚未解决的瓶颈

最终千问 profile 中，`traverseSuccessorsUntil` 仍占 6.80% inclusive 样本，`fillTypeCandidates` 为 9.00%，存活性为 2.39%。CFG 查询已经为每次遍历维护 visited BitSet；region 与指令在不同阶段继续变化，不能据此加入跨方法或全局的可达性缓存。类型候选对象按需转换后，类型更新、约束传播和字符串处理仍有明显分配。

`TypeUpdateInfo` 构造路径仍有约 6.72 GB 分配抽样权重。它在首轮 `verifyType` 前创建 IdentityHashMap；后续可先统计立即拒绝或始终没有更新的请求比例，再单独测试延迟创建工作表。需要保留 callback、回滚、更新次序、次数保护和中断检查；当前没有实施或测量这一候选，不能预估它的全量收益。

独立大样本的内联使用列表也需要继续研究。`ListUtils.safeReplace` 的合同是替换第一个相等项，找不到则追加，允许重复并保留顺序；方法和字段使用列表复制后替换，类使用列表可能原地修改。现有匿名类处理依赖列表长度及首元素，不能直接改成 Set、消除重复或缓存“未找到”。进一步优化需要先明确跨类写入、快照发布和消费次序，再单独测量。较大的使用关系索引和依赖生命周期调整留在方案中。

共同正确性基线之后的最终 DuckDuckGo 全量 JFR 有 24,280 个执行样本，132 个截断。`InlineMethods.updateUsageInfo` 占 inclusive 样本 59.99%，`ListUtils.safeReplace` 为 57.86%，`MethodInfo.equals` 自身为 57.65%；三者是嵌套调用，不能相加。`InlineMethods` 使用关系更新和 `safeReplace` 分别有约 78.20 GB、77.46 GB 分配抽样权重。此前的 hash 拒绝实验没有消除列表增长、线性查找和复制，其小幅变化不足以证明稳定收益，因此未重新纳入补丁。

没有检查 GUI、Windows、其他 JDK 的性能、资源输出、整份 APK 源码重编译或设备行为等价。现有 finally、throws 推断、方法别名和依赖卸载的顺序/并发问题仍是实质风险；这里保留具体输出与复现证据，不将全部非确定性差异判为等价。
