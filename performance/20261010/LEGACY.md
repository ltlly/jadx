## 测量范围与复现

详见 [REPRODUCE.md](REPRODUCE.md)、[corpus.tsv](corpus.tsv) 和 [benchmark.py](benchmark.py)。所有 APK 的全部 Java 类都经过正常加载、分析、代码生成和磁盘写出；资源输出关闭。它不是包含资源解码的 APK 总处理时间。

基线和各修改版在同一 checkout 构建并保存为独立分发包。Gradle 使用 Temurin 25.0.4.1，编译和测试使用 Temurin 11.0.32.1；性能运行固定使用 OpenJDK 27 build 27、`-Xms256m -Xmx16g -XX:ParallelGCThreads=3`、8 个反编译线程。每次新建 JVM 和输出目录。每组按 A1/B1/A2/B2/A3/B3 串行运行，不与构建、测试或 JFR 转储并行。

测量方法参考 [DDC performance engineering](https://github.com/ejfkdev/ddc/blob/b8bb5d02192840a2706595ee17391d86b7126b5c/docs/optimization.md)：先采样定位，再单项修改、重新采样和测量等量工作。本次没有采用 DDC 的跳过阶段、截止时间或原生内存分配器方案。

计时覆盖完整 Java 进程；输入、分发包和输出哈希计算在计时外。CPU 是 user + system 秒，RSS 是 `/usr/bin/time` 记录的进程峰值，含堆外内存。每次的命令、JDK、输入及所有 JAR 的 SHA256、退出码、标准输出、错误、文件清单、精确 diff 和主机 CPU 活动均保留。没有清除操作系统文件缓存，结果代表新 JVM、缓存逐步热身的交错运行。三次测量的区间是最小值至最大值，不是置信区间；增量收益不能直接相加。

## 质量证据与限制

原版千问已经返回退出码 3、报告约 1032 个错误，生成 71047 个 Java 文件。原版三次输出间有 71–82 个文件不同，其中约 58–65 个存在 Java token 差异，包括 try/catch 结构及方法体与占位体的变化。因此不能用单次字节相等作为本次质量结论，也不能声称 APK 已无错误地反编译。

最终重新运行的三轮千问基线占位体为 910/910/912 个，修改版为 903/916/913 个；逐方法检查没有发现三轮修改版都出现、而三轮基线都不存在的新增占位方法。这是检查结果，不是忽略偶发失败的许可。最终三对 A/B 的错误标记变化仅为同一 Base64 方法在 `StackOverflowError` 与 `JadxOverflowException` 之间切换，基线重复运行也出现相同切换。源码差异同时包含 try/catch 结构变化，需要结合算法对照和已有并发问题理解，不能按“注释变化”全部豁免。Telegram 三轮 A/B 的占位方法清单均为相同的 250 个，错误标记没有新增，但仍有源码结构差异。

另外检查所有修改版运行的占位方法并集，而不只检查稳定出现的占位方法。千问有四个方法在最终三次基线中没有出现占位体，但在更早、同一基线 JAR 的 `qwen-outer-A1` 中均已出现：高德 SDK 的 `g.a(Bundle)`、`h.a(Bundle)`、`k.a(Bundle)` 和 `kw.a(boolean,String,String,int)`。这些具体反例支持既有波动的判断，不能仅凭“稳定新增为零”得出质量结论。

[audit.py](audit.py) 保存缺失、新增和逐字节变化，并保存完整 unified diff。Java token 分类仅帮助审阅，不是 Java 解析器或语义证明。[quality.py](quality.py) 另存每个 `Method not decompiled` 占位体的方法签名，逐方法比较新增占位体和恢复的方法体。所有统计都与同一个 APK 的基线比较，不能用文件数和错误总数代替内容检查。

原版还存在并发生命周期问题：`MethodThrowsVisitor` 读取其他方法指令时可能遇到 `ConcurrentModificationException`；匿名类代码生成读取构造器参数时，依赖类可能已卸载。[ReproduceDependencyUnload.java](ReproduceDependencyUnload.java) 在未修改的基线 JAR 上控制处理顺序，重现相同的 `GENERATED_AND_UNLOADED`/缺失构造器参数错误；不插入依赖卸载时对照正常。它是控制实验，不是一次正常的全量 CLI 基线运行。这些既有问题仍然限制端到端输出稳定性。

DuckDuckGo 的 diff 还出现 `NavigationEventInput.dispatchOnBackCompleted` 的 `public`/`protected` 变化。[ReproduceVisibilityOrder.java](ReproduceVisibilityOrder.java) 在未修改的基线 JAR 上仅改变两个类的正常生成顺序：先生成目标类为 `protected`，先生成调用方为 `public`。跨类内联分析会扩大目标方法可见性，但已经输出的代码不会随之更新。该控制实验同样不是全量 CLI 性能测量；没有把可见性差异按注释忽略。DuckDuckGo 六次占位方法清单相同，均为 1480 个。

补充回归覆盖前驱小图穷举、CFG 环及 clean/full 边、bottom block 的候选优先级、根包名碰撞及快照继承、候选顺序与原停止条件、变量使用顺序和多父异常处理 region。诊断分发包还在同一运行时输入上执行旧算法和新算法，逐次比较返回值/有序候选集合；其额外工作和耗时不计入性能结果。生产 JAR 无计数器。

最终 core + CLI 完整测试共 1061 项，1060 通过、0 失败、1 项因 Java 11 工具链跳过 Java 17 profile（`TestConditions22`）。两个模块的 Spotless 和 Checkstyle 检查通过，见 [tests.legacy.tsv](tests.legacy.tsv)。逐项优化的相关测试也分别运行；这不是跨平台完整 CI 的替代。

最终诊断计数见 [shadow.legacy.txt](shadow.legacy.txt)。千问 4292308 次变量判断、Telegram 1414821 次变量判断与旧版完全一致，对应包含检查由 157647197 → 23368919 次及 79272375 → 9348959 次。命名、bottom block、outer switch 和有序类型候选对照也均为零不一致。活跃变量分析仅额外采集重复轮次计数，生产实现没有改动。

## 研究记录与未解决瓶颈

每项保留改动后重新采集千问完整 JFR，栈深度 256。CPU inclusive 统计对一个样本中的同一方法只计一次，分配字节为 JFR 抽样权重，不是精确分配总量。

基线有 25407 个 CPU 样本，其中 1429 个栈截断；最终千问有 17899 个样本，其中 291 个截断。各阶段样本总数及截断数保存在 [profiles.legacy.tsv](profiles.legacy.tsv)，跨阶段占比只用于定位，正式收益以无采样 A/B 为准。

* CFG 递归迭代器的分配权重由约 35 GB 降到约 4.9 GB。bottom block 调用者 CPU 占比随后由约 13–15% 降到约 1.6%；诊断版千问路径查询约 6098 万次降到 1031 万次，候选选择一致。
* 根包名复制约 26.9 GB 的分配权重消失，`NameGen.addNamesUsedInClass` CPU 占比由约 7% 降到 0.09%。
* 类型候选诊断中 `ArgType.object` 转换约 2.486 亿次降到 4648 万次，51406 份有序候选集合一致。类型候选重复命中率约 0.1%，没有足够证据支持增加候选缓存。
* region 包含关系存在普通父链之外的异常处理路径，region 在前面阶段也会变更。全局或跨阶段缓存缺少安全生命周期依据，本次没有实现。
* 活跃变量分析仍逐轮扫描 CFG 并分配 BitSet；改变扫描顺序或复用工作集可另行研究。类型边界检查、异常处理 region、代码生成和读取输入仍占耗时，较大架构改动未混入这些补丁。

最终 profile 中，`ProcessVariables.isAllUseAfter` inclusive CPU 样本占比为 0.54%（前一版 5.32%），其 HashSet 分配消失。`TypeSearch.fillTypeCandidates` 为 9.02%、`TypeUpdate.inBounds` 为 7.53%、`LiveVarAnalysis.processLiveInfo` 为 2.35%；活跃变量分析仍有约 6.5 GB 的分配抽样权重。该路径在千问执行约 1.247 亿次块扫描，值得后续单独测量工作集复用或遍历顺序，但不能把减少分配直接当成全量加速。JFR 各阶段前 40 项汇总见 [profiles.legacy.tsv](profiles.legacy.tsv)，分发包提交及 core JAR 哈希见 [builds.legacy.tsv](builds.legacy.tsv)。基线与最终版的分发包逐文件比较，只有 `jadx-core-dev.jar` 不同。

DuckDuckGo 的完整独立 profile 中，`InlineMethods.updateUsageInfo` 占 58.8% CPU 样本，`ListUtils.safeReplace` 占 55.8%，`MethodInfo.equals` 自身占 43.5%。`safeReplace` 线性查找旧项，找不到就追加；反复内联可使 usage 列表增长并重复扫描。这个路径没有被六项优化消除。usage 列表跨类更新，类的列表还会原地修改；`ProcessAnonymous` 根据列表数量及第一项作判断，因此不能把列表直接换成集合，或在没有写入版本信息时缓存“旧项不存在”。后续需要先明确顺序、重复项和并发更新的契约，再考虑在封闭阶段建立索引。本次没有实施该架构改动。

后续方案的验证边界：usage 索引必须保留“替换首个旧项、找不到则追加”的行为，并覆盖重复项、跨类更新及匿名类判定；CFG 索引只能服务已冻结边的结构查询，不能顺带缓存依赖可变指令的 predicate；region 索引必须表示异常处理 region 的多父关系，并在结构变更时失效。这些前提尚未证明，均未进入生产补丁。活跃变量工作集复用可作为较小的独立实验，但要先确认 BitSet 的所有权和固定点结果，预计收益也受当前约 2.35% CPU 占比限制。

另试过一行 `MethodInfo.equals` hash 预检查，复用已有不可变 hash，仍保留碰撞后的原比较。补充了方法名/类名碰撞、跨 Root 相等对象、重载和别名测试，完整 core/CLI 回归通过。单独 DuckDuckGo 三轮 A/B：A 中位 192.63 秒 [190.37, 195.46]，B 186.37 秒 [169.77, 199.35]；CPU 中位 424.29 → 418.09 秒，仅减少 1.5%，首轮墙钟反向。该候选未减少线性扫描次数，三轮结果不足以证明相对长尾波动有稳定收益，已撤回生产改动及试验测试，未加入交付补丁。原始分发包、差异、回归日志和六次测量均保留在 `out/jadx-perf/20261010/method-hash-check` 及 `experiments/method-hash`。

资源解码、GUI、跨平台安装包、不同 JDK/heap/线程配置及设备运行行为不属于本次性能结论。既有反编译错误、并发输出变化和依赖卸载问题没有修复；不能把这些补丁描述成字节稳定或无错误的反编译保证。
